# Track light files and the light editor

In Restomod '26 the light map of a track with no PS1 disc comes from a text file, one per track and time of day:
`data/track_light/<TRACK><A|B|C|N>.txt` (A dawn, B day, C dusk, N night). If something does not fit, it is changed in the file.
The files are generated by `tools/export_track_light.sh` with Restomod '26's settings and no disc; the PS1 disc's own light is never written (it is EA's and Sony's data).

## Which light the game uses

* **Restomod '26 with a file** (`<mod>/track_light/<file>`, else `data/track_light/<file>`): the file is used whole, every line, always. The port's settings that change how the light is made in code
  (`made_tunnels`, `canyon_shade`, `lamp_pool_tint`, ...) count for nothing here: what holds is the file. The canyon's and the tunnels' car shade follow the file's `canyon` / `tunnel` lines
  even with `canyon_shade` / `car_tunnel_light` off in the player's settings.
* **Restomod '26 with no file**: the light is made in code, as before.
* **Stock '96 and Restored '96**: the files are not read at all; the light is made in code as before (their goldens do not move).
* The header's `flags` is a record, "made with these settings". When it is not the settings now, the log gets one line (`track light: <file> was made with other settings (...)`) and the
  light editor a small line under the first one. It never changes which light is used.
* What the file does not hold, the settings still decide: the night lift, the lamp pools' brightness (`lamp_pool_bright`, `city_lift 3`), the headlight beam. Those are not the made light's map.
* `TNFS_TRACK_LIGHT_FILE=0` ignores the files (the code's light only); `TNFS_EXPORT_TRACK_LIGHT=<dir>` writes the code's light as files.
* A mod can replace a file: with `--mods <dir>` the lookup tries `<dir>/track_light/<file>` first.

The file a race reads is `<TRACK><letter>.txt`, the letter by the time of day (drive_light.c; checked in the log's "cannot read" lines for dawn, day and dusk, and in the code for night):

| time of day | file (TR2 as the example) |
|-------------|---------------------------|
| dawn        | `TR2A.txt` |
| day         | `TR2B.txt` |
| dusk        | `TR2C.txt` |
| night       | `TR2N.txt` (the night has its own file: the CD's C is the dusk) |

The light editor's header shows the track and letter (`LIGHT EDIT  TR2B  node ...`) and its second line the file in use (`track light: file <path>`).

## Format (a line a run of nodes, `#` starts a comment)

    track CY1 time N nodes 1920 flags dff     the header (flags: the settings the generated rows were made with, a record)
    rows 0 5 255 255 61 61 62 63 255 60 61 62 63    nodes 0..5 have this row of 11 points
    tunnel 1064 1171        road tunnel nodes (also hall, car_dim, canyon: the car's shade in TR6's canyon)
    pool 13 13 1           a street lamp's pool, class 1..4 (also car_pool)
    car_disc 1 <6 floats>   the car's brightness ratios in a tunnel's lamp alternation (hex floats)
    cast neutral 0 city 1
    tunnel_tone night 1.0 0.35 0.05 174    a warm tunnel's cast and its light in percent (day: the day's)
    brightness 120 180 70                     nodes 120..180 at 70 percent of their light
    car_tone ff8020:60                  the car's tone: a colour in hex and its intensity 0..100, the whole track
    car_tone 120 180 ff8020:60          the same for nodes 120..180 only (a later line goes over an earlier one)
    tone 120 180 ffe080:50              scene tone: nodes 120..180 are seen through a colour (hex) at 0..100 strength (yellower or whiter tunnels)
    tone 120 180 p6 p7 ff2020:60        only the row points p6 p7 (p0..p10): a side strip, e.g. beside a neon


`car_tone` takes each of the car's colours toward the tone at its own brightness, and shows the nearest colour the palette has, of any hue: a red car goes toward orange,
a white one to orange, a dark blue one stays bluish where the palette has no dark orange near. (`car_disc` only changes the car's brightness: a car's colours stay in their own hue family there.)

The words are English. The format's first version was Spanish (`pista hora nodos banderas filas presente tunel sala coche_tenue canon pozo pozo_coche coche_disco reparto neutro ciudad tono_tunel dia noche brillo tono_coche`):
the port still reads those words as the English ones, so an older file or an owner's edited one loads the same, and the export and the merge write English only.

The generated lines (`rows`, `tunnel`, `hall`, `car_dim`, `canyon`, `pool`, `car_pool`, `car_disc`, `cast`, and the `tunnel_tone` the code starts with) are what the export writes.
`tone` tints the road, walls and scenery of those nodes (the tint is 1 + (colour/255 - 1) x strength, applied to the lit colours; in a tunnel, over its cast). A track has at most 16 distinct tones (a 17th is a bad line); each is built the first time it is seen (about 2.5 ms and 4 KB). A later line over the same nodes replaces the earlier. A polygon takes a tone only when all four corners have it, so a strip follows the row points. The light editor shows the current stretch's tone.

`brightness` and `car_tone` are lines added by hand; the editor's F11 writes a `brightness` line. All of them count the same.

## The weather and the tunnels (Restomod)

A `tunnel` line is also a closed zone for the weather: inside it there is no rain, no fog, no rain's haze, no lens drops and no lightning, and the thunder is muffled to 40 %. All of it fades in over the 6 nodes outside a mouth
(the light editor shows `weather: open|closed N/16` for the node). Coastal's galleries, which the road marks but the files do not, count as closed zones too. A `hall` is not a closed zone (TR7's steelworks, `hall 1 62` and `hall 1011 1023`,
has rain; its tunnels, `tunnel 465 470`, `571 609` and `682 695`, do not), and a `canyon` is open air (Alpine's, `canyon 600 771`, rains). Stock and Restored have no weather of their own and are not changed.

## Regenerating the files (the owner's edits survive)

When a change to the engine alters the light it generates, the files are regenerated with `tools/export_track_light.sh <bin> <original/> [dir]`. The export does not write over the files:
it goes to a scratch folder and `tools/track_light_merge.py` merges it with the file in `dir`, a three-way merge against the last export, which is kept gzipped in `dir/generated/<file>.gz`:

* a thing that differs from the last export is the owner's edit and stays: a node's row, a node's membership of `tunnel` / `hall` / `car_dim` / `canyon`, a node's `pool` / `car_pool` class,
  the `car_disc`, `cast` and `tunnel_tone` lines, and every line the export never writes (`brightness`, `car_tone`, comments);
* what he did not touch is the new export's, so its news arrive (a longer tunnel, a moved lamp pool, new rows);
* the header (`flags`) is the new export's, the record of the settings it was made with;
* a file with no last export on record keeps its content and only renews its header (with a warning); `FORCE=1` writes the new export over everything, as the first export did;
* the new export becomes the record, so commit `generated/` with the files.

If the node count changed the merge stops for that file (it is kept as it is and named): regenerate it by hand. `tests/test_track_light_merge.py` keeps a hand-edited file alive through a regeneration.

## Light editor

`light_edit=1` in `port.cfg` (or `TNFS_LIGHT_EDIT=1` as a launcher) shows, in a race with a made light, the node the car is at, `track light: file <path>` or `track light: made in code (no file for ...)`,
and the values there. F10 holds the race where it is, F11 copies a `brightness N N 100` line to the clipboard. Saving the file reloads the light within a second, without leaving the race.
